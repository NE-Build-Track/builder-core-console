# 29 October 2026: repeat-safe commands (builder-core D57) on the live stack

**What ran.** The console stack at `be77a01` (PR #10 merged), with the engine at builder-core `a6ed9b5` (the
merge of builder-core #76), Clearinghouse Batteries `ca09e47` and the livepeer/node signer `406b248`, paying on
Arbitrum One. `ENGINE_PORT` was moved to 8092 because a host process holds 127.0.0.1:8090. On start the
engine upgraded the existing `engine-data` volume from migration `0008` to `0010` (the job retry columns and
the operation ledger) with no reset.

Two scripts, both in this repository: [`scripts/live-check-d57.py`](../../../scripts/live-check-d57.py)
through the engine's REST API, and [`scripts/live-check-d57-ui.py`](../../../scripts/live-check-d57-ui.py)
through the Operator page in headless Chrome. Each run makes its own grant and actor.

## Through the engine: 37 checks, all passing

| Area | What was shown |
| --- | --- |
| References required | All seven commands that move money or create a key (create grant, fund grant, provision, fund allocation, rotate payment key, issue key, rotate key) answer 422 without an `operation_ref` |
| Grants | A created grant reads back in full (name, status, total) and carries `metadata.lpb_operation`, stored and listed by Batteries. A repeat replays it (`Idempotent-Replayed: true`); another amount under the same reference is 409 `operation_conflict`; Batteries holds exactly one. Funding it twice under one reference took its total from 0.50 to 0.60 once |
| Provisioning | A repeat replays the actor; another amount under the same reference is 409 `operation_conflict`; a new reference on the provisioned actor is 409 `already_provisioned` with the actor, and its 0.03 was not applied |
| Allocation funding | A repeat replays; the allowance reads 0.05 + 0.02 = 0.07, funded once |
| Access keys | A repeated issue answers 201 with `token: null` and `replayed: true`, and the actor has one key. A repeated rotation does the same; the rotated key runs a paid job and the old key is refused (401) |
| Payment key (B1) | A repeated payment-key rotation replays the same new key, and a paid job afterwards still pays: the live key was not revoked |
| Jobs | A repeat after a paid job succeeded is 409 `operation_exists` with the same job id; another body is 409 `operation_conflict`; a repeat while a stream ran is 409 `operation_in_progress` with `Retry-After`; a job that failed before dispatch (`no_offering`) ran again as a new job under the same reference |
| Cost | After cost sync, the test actor's reconciliation is balanced with nothing pending or unattributed |

The first run had one failure in the script itself (it parsed the streamed response as JSON); the
fixed script passed every check on a fresh actor. The committed scripts were then run once more on the
same stack (images rebuilt from the same pins): 37 of 37 and 14 of 14.

## Through the console: 14 checks, all passing

| Check | What was shown |
| --- | --- |
| References | Each Operator dialog carries its own `console-<action>-<uuid>` reference |
| Create a grant | "Grant created"; Batteries holds the grant once, tagged, total 0.25. The API replay of the UI's own reference answers `Idempotent-Replayed: true`: the console sent it, and a repeat applies nothing |
| Fund an allocation | "Allocation funded"; the API replay of the UI's reference is a replay, so it applied once |
| Provision an existing actor | "HTTP 409: this actor is already provisioned, so nothing was applied, the amount included. Fund its allocation instead.", with "Start over (new reference)" |
| A reference used for another request | The dialog says the engine did not apply this one and offers "Start over (new reference)"; no grant was created |
| Issue a key | "Key issued" with the token shown once; the API replay of the UI's reference answers 201, `token: null`, `replayed: true` |

Every page (`/`, network, sources, money, users, usage, jobs, operator, builder and its jobs and usage)
answered 200 with no error; Health read Operational.

## Demo traffic and reconciliation

One batch of `scripts/demo-traffic.py --yes`: chat jobs succeeded for every actor and the deliberate bad
request answered 400. The embedding jobs failed as `no_offering` with no attempt: no discovered orchestrator
advertised `blueclaw/embeddings/ollama` that evening. After cost sync, alice, bob, carol, dave and both
test actors were each `balanced`, with nothing pending or unattributed. Everything together cost well under
a cent.

interrupted before its first attempt. builder-core's own tests cover those.
