# Decisions

Accepted 20 October 2026 by Mike unless noted. D14 was added and D5 revised the same day. On 21 October Mike made the console the M3 reference app: D15–D20 added, D1 and D7 revised, D13 superseded. Changing one needs a human (AGENTS.md).

| # | Decision | Why |
| --- | --- | --- |
| D1 | ~~**The console is read-only in v1.**~~ *Revised 21 October:* the existing pages stay read-only; writes happen only in the Operator actions and Builder areas (D15), each behind its own sign-in (D16). Only GET reads of the engine, Batteries and the signer. No forms that post, no route handlers or server actions that write. | A management view should be safe to leave open. The engine admin key can do anything (gap G8), so read-only is enforced in code by `tests/structure/read-only.test.ts`. |
| D2 | **The engine is the stock builder-core REST service**, `lpb serve` built from builder-core `4041ffe` on `tasks/mz/admin-read-actors` (26 October, local Keycloak test: PR #53 on #50, JWT bearer and the actor collection, on `releases/m3`, which has #46 and #48; before that `d057935`, PR #48, key inspection and rotation; and `985f23d`, builder-core #45, the discovery service runs beside it as `lpb discovery` from the same image, and the signer only signs, D43; re-pin to the merge on `releases/m3`); before that `629f1ab` on `releases/m3` (moved 24 October to the merge of PR #44, after PR #43: cost reads never stale and payment evidence before the paid request, migration `0005`, the commit ChatLPT pins; on 23 October to the dependency-injection refactor, PR #41, then to the merge of its follow-up PR #42, `878e4f4`; before that `ad6bba9` on `releases/m3`, the merge of PR #28 and PR #31, from 21 October; earlier that day `93756ba` on `tasks/m3/mz/stream-support`, before that `a89216d`) and run as its own container. Not embedded. | The console reports on the engine as builder-core ships it, so whatever it shows is true of every stock deployment. `a89216d` is a superset of `releases/m3` (streaming, `abandoned`, runner GPU). |
| D3 | **The stack's own payment stack uses ChatLPT's pins, configuration, env names and secret values.** Only one of the two stacks runs at a time. | Same payer, same orchestrators, no new credentials to fund. One signer per payer account (ChatLPT D10). `first-run.sh` never starts the signer. |
| D4 | **Next.js App Router with server-rendered reads; no Gyral.** The browser never talks to the engine or Batteries. | Credentials stay on the server; pages are plain server components. |
| D5 | **Tailwind v4 and shadcn's token setup stay; the console's components follow the design system in D14.** Semantic HTML for structure; modern CSS for layout, tokens and motion. *Revised 20 October:* v1 first used shadcn's generated Card, Table and Alert; D14 replaced them with the mock's own components, so `components/ui/` is empty. shadcn's colour names map onto the console's tokens, so a shadcn widget added later matches. | The semantic-html and modern-css skills apply to everything: landmarks, captions, oklch tokens with `light-dark()`, container queries, cascade layers, motion gated by `prefers-reduced-motion`. |
| D6 | **Compute on demand; store nothing.** Each page reads current state; a 15-second in-memory cache shares reads. | The engine already stores projections and Batteries the ledger. Local rollups and Prometheus are future work (tech debt). |
| D7 | *Revised 21 October:* the read-only pages need no sign-in on 127.0.0.1 and keep the server-configured admin key; Operator actions and Builder need a sign-in (D16). Originally: **No sign-in in v1.** The console is published on 127.0.0.1 only. | It cannot move money (D1), but it shows every actor's spend. Auth is future work. |
| D8 | **Batteries is the money authority; the engine is the attribution authority.** | Batteries applies every signed ticket; the engine knows which job and actor a ticket paid for. The console shows both and their reconciliation. |
| D9 | **The engine runs in its stock `per_actor` mode.** | Grants, actors and per-actor allocations are what a management view is for. ChatLPT's `per_application` shared key does not apply. |
| D10 | **Signer metrics through a socat relay.** | The signer refuses non-loopback metrics binds (gap G5). The relay shares its namespace and is never published. |
| D11 | **One engine.** The console reports on the stack's one `lpb serve` engine, not on other engines that might pay through the same Batteries. | Scope. Spend from elsewhere would show as unattributed. |
| D12 | **Engine types come from the pinned spec; Batteries and signer shapes are zod schemas.** | The engine publishes OpenAPI at the pinned commit; the others do not. |
| D14 | **The visual design is the accepted mock**, `design-docs/mock/console-mock.html` (accepted by Mike, 20 October 2026). Its stylesheet is ported layer for layer into `web/src/app/globals.css`, and its widgets became components on real data. What the mock faked is either real or labelled: signer sparklines show samples since the page opened (D6), the ticker shows Batteries' newest applied tickets, the topology's packets only flow on healthy edges. | It is the design Mike wants; porting rather than reinterpreting keeps it faithful. |
| D13 | *Superseded 21 October by D15.* **Writes happen outside the console**, through the engine's Swagger UI or curl on 127.0.0.1:8090. | Keeps D1 while the stack is still operable. |
| D15 | **The console is the M3 reference app** (Mike, 21 October). Beside the read-only pages it gains two areas: **Operator actions** (signed in with the admin key: create and fund grants, provision actors, issue, inspect, rotate and revoke keys, set allocation status) and **Builder** (signed in with an actor key: the seven outcomes over REST, from catalog and rates to a job, its result or failure, my jobs, allowance, usage and network cost). Folded in rather than a new app. | One stack, one design system, one place showing the REST API for reads and writes. The M3 gate is the builder's journey; the read-only pages are the operator's view of it. Covers ISS-20, ISS-21 and ISS-22, and the admin side of ISS-08 and ISS-11. |
| D16 | **Sign in by pasting a key** (Mike, 21 October): an admin `lpk_` key for Operator actions, an actor key for Builder. The server keeps it in an httpOnly session cookie and the browser never reads it; each page shows only what that key may see. | Demonstrates outcome 1 (obtain one credential) and keeps keys off the client, as D4 does for the server-configured key. |
| D17 | **Every write is fill in → review → result** (Mike, 21 October). Nothing is sent before the review is confirmed; the result is a toast plus the refreshed section. Money moves (fund grant, fund allocation) show the amount and the balance before → after; actions that cannot be undone (revoke key, revoke allocation) need the key's prefix typed; a new or rotated key is shown once with a copy button, then only its prefix; everything else is review only. Each form carries an operation reference so a repeat cannot apply twice, once the engine honours one on admin calls (ISS-11, T2). | Writes stay deliberate and safe to leave open; repeats are a contract question for the engine, not something the UI can guarantee alone. |
| D18 | **Every action shows its REST call** (Mike, 21 October): a "The request / The response" panel with method, path, body and status, keys hidden, and copy as `curl`. | The app is a reference for how to use the REST API, so the call is part of the page, not hidden behind it. |
| D19 | **One generic job form, fed by the live catalog** (Mike, 21 October): pick an offering from `GET /v1/offerings` (rate with its unit and freshness; missing or stale said so), a path, a JSON input and options (stream, timeout, max attempts). Example inputs are app-side presets for chat and image until the engine describes each capability's inputs (builder-core #18); any other offering starts from `{}`. | No bespoke screen per capability (ISS-21); a new offering appears without editing the app. |
| D20 | **Output views follow the response's content type** (Mike, 21 October): server-sent events and text stream as they arrive, JSON pretty-printed with any image URLs shown, `image/*` shown directly, and **Raw** (the exact bytes) always available. The one format-aware view is **Rendered** for chat, which joins the reply's text pieces. Failures show the engine's failure kind, message and whether payment went out. | Builders see the API's real shape, which is what they copy; one rendered view keeps chat readable. |
| D21 | **Sign in through an identity provider, by configuration** (Mike, 26 October; local Keycloak test of builder-core #50 and #53, not merged). `CONSOLE_AUTH=oidc` replaces pasted keys: the console is an OpenID Connect client (`openid-client`, OpenID-certified, confined to `adapters/oidc/`) running the authorization-code flow with PKCE on the server. The provider grants each area its scope (`livepeer:admin` for Operator actions; `jobs.run` and the reads for the Builder), the engine (`LPB_AUTH=jwt`) checks every token, and a builder is the actor its `sub` names. Tokens stay sealed in the area's cookie and `src/proxy.ts` refreshes them before they expire; sign-out also logs out at the provider. The background reads use the console's own read-only client-credentials token (`console-reader`, an auditor), so there is no admin key on the read path (gap G8 does not apply). Key actions are hidden because the engine's keys are off. | The identity provider owns people and the engine owns actors; no long-lived credential sits in the console, and the read path cannot write even by mistake. Pasted keys stay the default (D16). |
